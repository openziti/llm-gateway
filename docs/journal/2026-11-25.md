# 2026-11-25

## Local-inference epic: desktop client design session

The [client spec](../future/local-inference-client.md) was drawn. No code changed. This entry holds what the spec does not carry. Decisions below are Michael's, made in conversation; anything marked **(proposed)** in the spec is the design agent's and unconfirmed.

### Decisions

- **The client is a thin pass-through, not the gateway in a client configuration.** Michael's reason: people running local inference install the gateway in their infrastructure and hand out access, and each user installs the tray daemon, which binds the lab to `localhost`. Two things follow for the hub spec: "credentials toward local endpoints" and "booting without overlay-dialed backends" both stay deferred, because the client is not a gateway. The two lines in the hub spec's Deferred section that pointed those at the client were corrected.
- **Yesterday's line "the client acts as root" is supplemented, not replaced.** The owner at the laptop is root. Other people run the same client at their key's level.
- **`dfw` gains an optional cookie shared between a window and its server.** Carded in the `dfw` repo as `window-cookie.md`. The client depends on it. Michael committed the card there (`c2ea633`), and another session then drew its spec at `docs/future/window-cookie.md` and moved the card to researching. This session's later edit to the card, recording that `dfw` makes the check itself, sits uncommitted in that working tree beside the other session's change. This session did not read or touch that spec beyond its opening lines.
- **The hub's share is closed.** Michael: zrok shares are closed by default. Checked below.
- **Linux and Windows first, macOS later.**
- **This repo, this branch, with good dependency hygiene.** The mechanism is not chosen. See live state.
- **Status by polling.**
- **The client is a "dongle" for one system.** Michael's word, given with the loopback ruling: it gives that specific system's user access to the inference infrastructure. The framing is the system, not the account. That raised the question of a second account on the same machine, which the key reversal below settled.
- **The door passes the caller's key through and adds none. This reverses a call Michael had confirmed an hour earlier.** The first ruling was that the door discards whatever key an assistant sends and attaches the client's own, so an assistant needs only an address. Asked whether a second account on the same machine using the door was a gap or by design, Michael saw that the lending of the client's key was the cause and reversed it. A hybrid that passes a key through when one is sent and adds the client's when none is would keep the problem, so the door adds nothing at all. Consequences that are easy to miss: the client still holds a key, used only for its window; the door works whenever the hub is reachable, even in *key refused*; and an owner can keep root in the client while assistants carry a consumer key. A separate local secret on the door was ruled out because it costs the user the same paste with more machinery. Attaching the client's key survives only as a Deferred item, as something a user might turn on for a machine they alone use.
- **The goal is a very user-friendly client.** Michael's words, given as the reason for staying up when it cannot connect. Weigh the remaining proposed calls against it, the deferred conveniences especially: enabling zrok from the client, one invitation in place of a token and a key, and installers.
- **Every zrok share the gateway creates becomes closed.** Decided after the card was written, so the card now carries the instruction and not the question. It was not implemented in this session. At Michael's ask it was then folded into the client spec, under "What the Hub Gains", so the client's work order carries it; no work order exists yet. That ties it to the last of the example's three pieces of work, though nothing in the example depends on it and it matters for `main` whether or not the branch merges. The card stays as the roadmap item pointing at the spec. `newShare` is the only place the gateway creates a share, and it serves both modes, so public shares become closed too, as zrok's own CLI makes them. Two things on the card began as the design agent's reading and Michael later confirmed both: a list of accounts to grant in `zrok.share`, needed because a closed ephemeral share is otherwise reachable only from its owner's account and its token is new on every start, and no opt-out back to open. Shares attached by token are untouched, since the gateway did not create them and cannot see their mode.

### Read from source

- **`dfw` v0.1.7.** `webview` needs cgo and native headers on every platform. By its docs `tray` needs cgo on macOS and not on Linux. A window navigates to the bare daemon address (`webview/window.go`), and `WindowApp` has no field for a path or a header, which is why the cookie has to come from `dfw`. It has no single-instance enforcement and no packaging. Its tray menu's items are fixed at startup; only labels, enabled state, icon and tooltip change afterwards. Its CI builds Linux and macOS and not Windows.
- **`dfw` and `df`.** `dfw` pins `df` v0.3.14 and this repo is on v1.0.2. The six `dd` and `dl` functions `dfw` calls exist by name in v1.0.2. It was not compiled.
- **zrok v2 rc5.** `zrok2 create share` and `zrok2 share private` create shares closed unless `--open` is passed. The controller lets an account reach its own closed share with no grant (`checkAccessGrants`), answers 401 to an account with no grant and 404 to an unknown token, and `zrok2 modify share --add-access-grant` adds an account by email to an existing share. `CreateAccess` authenticates with the environment's account token, so every user needs an account on the same zrok service. None of this was exercised, only read.
- **Enabling a machine is not one SDK call.** `sdk.EnableEnvironment` reads the account token from `root.Environment()`, which a machine that was never enabled does not have. zrok's own `enable` command instead calls the service's enable endpoint with the token, then `SetEnvironment`, then `SaveZitiIdentityNamed`, all through packages this repo already imports. The service address comes from the root's `ApiEndpoint()`, so a self-hosted zrok service has to be set in zrok's config first. The design agent told Michael the SDK call would do before reading its body; the ruling that the client enables the machine stands, at a somewhat higher cost. Michael's answer: the zrok SDK can be amended if that turns out to be the better home for it.
- **The gateway overrides zrok's default.** `newShare` passes `OpenPermissionMode`, so a share the gateway creates for itself is open. `NewShareFromToken` neither sets nor checks the mode of a share it attaches to. Carded as `gateway-created-zrok-shares-are-open.md`.
- **The house `desktop` subcommands, read from mega** (`cmd/mega/desktop.go`, which its docs say follows ranger's). `desktop integrate` writes a desktop entry and hicolor icons under the XDG data home, and `desktop remove` removes exactly those files. It refuses on anything but Linux, so Windows integration is new work for the client. Its launcher runs the daemon through the user's shell by default, because mega runs tools from that shell; the client has no such need. mega's docs say "No autostart", so starting at login is new for the client too. `dfw`'s own example still has the older `install-desktop`. One Windows wrinkle from `dfw`'s build docs: a binary linked for the GUI subsystem has no console for any of its subcommands, so a subcommand's output is not seen there.
- **`docs/current/zrok.md` names v1 commands** (`zrok reserve`, `zrok enable`). v2 has `zrok2 create share` and `zrok2 enable`, and no reserve command. Not edited.

### Canon the client spec will meet

Flagged, not edited.

- `stream-integrity` is why the door is not a pure byte relay. A relay that just cuts a broken stream is what that quality flags, and on a laptop a stream cut by sleep is the common case. Michael ruled that the door ends a broken stream with an error event, so the quality holds for the client as written and needs no statement. The door therefore knows where a stream's events end, and reads nothing else.
- `explicit-config-fails-loud` asks for a boot refusal. Michael ruled that the client stays up and shows the problem, for connection failures and for settings it cannot read alike, because a tray program that exits is silent. Only failing to open its own listeners ends the process. The quality needs a statement saying so, and if the client lands under `cmd/` it is in that quality's territory.
- `openai-front-door`: the door's own 503 goes through `providers.WriteError`. The window's server is a second surface with no OpenAI shape.
- In `dfw`'s canon, `product-owns-the-http-boundary` names authentication as the product's and flags library handlers on the supervised server. Michael ruled that `dfw` does the check itself, so that quality needs an exception. The cookie card records the ruling and the shape set aside.

### Live state

- Michael ruled on every proposed call in the client spec, one at a time in conversation, and no mark is left in it. He has not read the spec through, and three kinds of thing in it were never put to him singly: the contents of the Deferred list, the list under "What Has To Be Tried First", and the wording of the scenarios. The hub spec still carries 7 marks and the harness spec 6. What he confirmed: the door forwards `/v1` only; the door passes the caller's key through (reversed from discard and replace; see Decisions); the door is loopback only (also "to start", also listed as deferred); the client enables zrok on the user's machine itself, so nobody installs the zrok CLI; setup is a page in the window, and an advanced user may instead write the settings file by hand and start from it; one client talks to one hub ("to start"); the client reconnects on its own after sleep or a network change; a request arriving while it is not connected waits a few seconds and is then served or refused with a 503 naming the state; the hub tells any valid key its level, its name, the models it may use, and the hub's version, which is an addition to the hub spec's status surface; the client keeps its door's own in-memory list of recent requests; polling runs at two rates, frequent while a window is open and a slow check otherwise; the daemon relays the hub's status data to the page with no transformation of its own ("there's no reason for the extra layer"); the client tolerates a hub of another version, showing what it does not recognize as the hub named it; a claim from the window takes an optional note and a choice between the host's grace and none, and is previewed first with a warning read from the snapshot; the door refuses requests not addressed to localhost and requests a browser makes for a page from elsewhere; the setup page asks for a self-hosted zrok service's address, hidden by default behind a link along the lines of "do you run a custom zrok?"; a machine already enabled on a different zrok service is reported and left alone; the client ships as a plain archive, starts at login as a setting the user turns on, and carries the `desktop integrate` and `desktop remove` subcommands the other `dfw`-based programs have; the window offers "add to my desktop" and "start at login" as switches too. On the Windows side of `desktop integrate`, Michael: "we'll figure out the windows issues", so the spec leaves it to the work order. Last, a plain URL may stand in for a share token, in the hand-written settings file only.
- Five things are untested and the spec lists them under "What Has To Be Tried First". The sleep and wake question can be tried with today's binary: run the gateway on a laptop with `providers.local.zrok_share_token` pointed at any share, suspend, wake, and time the first request.
- An observation for whoever tries the registration question: `sdk.DeleteAccess` needs only the frontend token and the share token, so a client could remember its access and remove or reuse it at the next start. Whether zrok lets an old one be reused is not known.
- Not decided: the binary's name, what the page is built with, and how the client is kept out of the server's build. For the last, a nested Go module keeps `webview_go` and `systray` out of this `go.mod` but needs a replace or a workspace to import the gateway's packages. A build-tagged package in the same module is simpler and leaves both in `go.mod`, though the server binary links neither. `make test` runs `go test ./...` and `go vet ./...`, and the Makefile convention wants the ordinary gate to cover frontend work where present, so how the client's gate joins it is a real question for the work order.

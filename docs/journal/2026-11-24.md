# 2026-11-24

## Local-inference epic: design session

A design session opened the `local-inference` epic ([card](../future/roadmap/local-inference.md)). No code changed. Two specs came out of it, the [hub](../future/local-inference-hub.md) and the [harness](../future/local-inference-harness.md); this entry holds the decisions that span them and the reasons the specs don't carry. Every decision below is Michael's, made in conversation.

### Decisions

- **The gateway is installed infrastructure, not laptop software.** One path at two sizes: on the inference host when there is one host, on whatever stays on when there are several. The example is a hub on the LAN reaching backends by LAN URL, with the laptop coming in over a zrok private share.
- **The working example is what gets socialized, not a document.** The branch merges to `main` or does not on the strength of it. That is why the epic card carries a walk-through as its acceptance target and there is no umbrella design document.
- **Nothing crosses from local to hosted on failure.** That is today's behavior and it is the guarantee. Opt-in hosted fallback is wanted eventually and deferred.
- **User types are levels on the virtual key, on one door:** consumer (every key today), read-only (adds status), root (adds control). Root comes only from the gateway's own config, never from a file or HTTP key source, so a remote key source cannot mint an owner. A separate control door was considered and set aside because the owner is assumed to be the only root user. Revisit when root is offered over a public share.
- **Control goes through a per-host harness, not SSH from the hub.** The real operation on these hosts is `systemctl --user` start and stop, so the control dialect is systemd rather than any inference server's API, and one harness covers vLLM and the custom engine alike. The harness knows only engines declared in its own config; the hub sends a name and a verb, never a command. It stays out of the inference path. SSH was rejected because it puts a credential with shell reach on the hub and gives host statistics no home.
- **Systemd user units are the only engine runner in the initial build; Docker containers and similar are expected if the branch merges.** So the harness spec draws the runner seam now with one implementation: an engine names its runner in its own config block, engine states are runner-neutral, and any runner may start and stop only what the host already defines. Docker daemon access is ordinarily root-equivalent, which the harness's unprivileged footing will have to answer when that runner is designed.
- **A GPU claim is owned by the host's harness; the hub requests and reflects it.** Reasons: it survives a hub restart (the hub keeps no persistent state), it can be made at the machine without the client, and the host enforces it by refusing to start anything on a claimed GPU. Core behavior: stop routing new requests, grace period for in-flight, stop the engines, fail fast with a reason for models left with no engine, and release restarts exactly what the claim stopped. Standby engines are designed for but not built.
- **History is a bounded in-memory window in the hub,** lost on restart. A persistent store may come later.
- **Raw ziti is in the epic and outside the example,** built last.

### The example's hardware

Four hosts that never sleep: a 2080ti running whisper and embeddings, a 3090 running qwen3.8-27b, a 4090 currently unused, and a 5090 running a custom inference engine for qwen3.8-27b. Some engines are vLLM. Engines are stopped when a user-facing application needs the GPU, which today means SSH and `systemctl --user`. Whisper and embeddings are inventory only; the gateway fronts chat completions alone and those routes are deferred.

### Read from the code, relevant to the specs

- `MultiLocal` selects endpoints without looking at the requested model, while `ListModels` returns the union. A model hosted by one endpoint gets the other endpoint's not-found error on about half of requests, and application errors do not fail over.
- The health probe already fetches each endpoint's `/v1/models` and discards the body.
- Metrics and usage records name the provider (`local`) but never the endpoint, and streams record only total duration. Which host served a request, time to first token, and tokens per second are all unmeasured.
- `Local` sends no `Authorization` header upstream, so it cannot reach a backend or another gateway that requires a key.
- **Only overlay-dialed endpoints can fail the boot.** A failed zrok access for any endpoint is fatal at startup; a `base_url` endpoint whose backend is down boots fine and is marked unhealthy by the probe. The example has no overlay-dialed backends, so "booting without backends" is deferred. Building it would also need an amendment to the `explicit-config-fails-loud` quality.
- The gateway's own zrok share is ephemeral unless a token is supplied, and is created in open permission mode.
- The ziti SDK is used only underneath the zrok access path. There is no raw ziti config surface in either direction.
- All four release configs build with `CGO_ENABLED=0`. A webview client wants its own binary and release path so the server binary stays static.
- `/metrics` is unauthenticated and carries per-key usage.

### Canon the specs will meet

Flagged, not edited; canon changes are Michael's, in terminus-canon.

- `openai-front-door`: the status and control surfaces are the first client-facing surfaces with no OpenAI shape. The quality needs a boundary statement for a gateway-native surface.
- `deny-not-reroute`: a catalog alias would be a new resolution step and must land before the permission checks. Hosted fallback changes what runs after the check and would need the check repeated.
- `failover-network-only`: unchanged inside a model's pool. A model with no running engine becomes a gateway-originated error, which is new.

The hub spec fixes the defect on this branch, so the card matters only for `main`. Its second symptom, `provider '' is not configured`, is read from the code and not reproduced.
- `dfw` is `github.com/michaelquigley/dfw`, Apache 2.0 per Michael. It is not on this machine and was not inspected; whether it needs cgo is unverified.
- Michael believes the 3090 and 5090 engines both report `qwen3.8-27b` as the model id; it has not been checked against the engines. Pooling them depends on it, or on catalog aliases, which are deferred.
- The hub spec is drafted at `docs/future/local-inference-hub.md` and not yet read by Michael. Calls marked **(proposed)** in it are the design agent's and unconfirmed; do not plan against them until he has made them. Three were confirmed after drafting and are no longer marked: a `models:` declaration replaces discovery for its endpoint, read-only keys come only from config like root, and `/metrics` stays auth-exempt as an accepted gap.
- The harness and control spec is drafted at `docs/future/local-inference-harness.md`, also unread, with its own **(proposed)** calls. The one most likely to be planned against by mistake: the claim's grace period is owned by the harness, not the hub, so that a claim made at the machine works with the hub down. A design that has the hub drain and then tell the harness to stop would break that. Four calls were confirmed after drafting and are no longer marked: the harness-owned grace period, where a claim is enforced (start requests and harness startup; a hand-started engine is reported, not stopped), refusing a public zrok share when any harness is configured, and the config split (the hub links endpoints to engines; each harness says what an engine means on its host).
- Each drafted spec still has six smaller calls marked **(proposed)**. The hub spec's next phase is either a spec-only review or a planning agent for its work order; Michael has not chosen.
- Still unwritten: the desktop client spec and the raw ziti spec. See the handoff below.
- The embedding and classifier calls for semantic routing use a second, separate model-blind rotation (`roundRobinTransport`). The hub spec brings them under the catalog; a fix to chat routing alone leaves that copy behind.

## Handoff: the desktop client design session

Nothing about the client is specified. This is what was said about it, sorted by how settled it is, so the next session does not mistake a suggestion for a decision.

### Decided by Michael

- There is a laptop-side GUI client for local observation and control, and it reaches into the hub. In his words, that level of control is where the value lies in this kind of setup.
- It is built on `dfw`, as its own binary with its own release path. The details are to be worked out.
- The person at the laptop owns the infrastructure, so the client acts as root.
- zrok is the overlay for the example.
- He wants whatever operational statistics the hub can show, and he wants to claim a GPU from the client.

### Suggested by the design agent, not ruled on

- The client's engine could be llm-gateway itself in a client configuration: a local listener the assistant points at, with the hub as its one upstream over the overlay. The laptop would then need no `zrok access` process or tunneler, and the client would have its own usage records for this laptop's requests.
- Opt-in hosted fallback would sit most naturally in the client, with hosted keys on the owner's own device.
- The client should not gate the first usable path. The hub can be used with `zrok access` and `llm-gateway status` before the client exists.
- Whether status reaches the client by polling or a pushed stream. The hub spec leaves this to the client spec.

### Not yet looked at, and needed first

- `dfw` itself: what it wraps, whether it needs cgo, and what it asks of a release build.
- How a zrok access behaves in a long-running laptop process across sleep, wake, and network changes. The health checker in `providers/multiLocal.go` already treats a long gap as a sign that zrok sessions are stale and staggers its checks; a laptop meets that condition constantly.
- How the client presents a key to the hub. `Local` sends no credential upstream.
- The hub's own zrok share is ephemeral unless a token is supplied. An installed hub wants a persistent one, or the client's configuration breaks on every hub restart.

### Raw ziti

Michael wants raw ziti supported as well as zrok. It is a third transport beside zrok and Agora, in both directions, outside the example and built last. Nothing is designed. The one observation made: with a ziti tunneler on the laptop the hub appears at a stable intercepted hostname with no per-share process, at the cost of someone running a ziti network.
